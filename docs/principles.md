# Design Principles

## Specification Before Implementation

AMTS defines conventions.

Implementations follow the specification.

No implementation defines the specification.

## Implementation Independence

AMTS is independent of any specific assistant, model, language, framework, software project, or vendor.

Any implementation may adopt AMTS without changing its meaning.

## Documentation First

The specification is expressed through documentation.

Documentation is the primary artifact of AMTS.

## Human Readable

AMTS documents should remain understandable by humans.

The structure should be simple enough to inspect, review, and maintain manually.

## Assistant Friendly

AMTS should enable reliable initialization, collaboration, and handover between assistant sessions and assistant environments.

## Minimal Complexity

Only introduce additional concepts when they provide clear value.

Prefer simple structures over complex ones.

## Stable Evolution

AMTS should evolve incrementally.

Changes should preserve compatibility whenever practical.

## Explicit Decisions

Important conceptual, structural, or compatibility decisions should be documented.

The reasoning behind a decision is often as valuable as the decision itself.

## Reusability

AMTS should be reusable across different projects and organizations.

## Open Evolution

AMTS should support future assistants, workflows, and implementations without being tied to any one of them.
